fix: bound the pair search in work and report a capped search in the scan

Three findings from the code review on PR #78, all reproduced before the fix:

1. The scan swallowed the coverage. It called vertical_spreads without a
   coverage dict, so a section that hit MAX_PAIRS_PER_SECTION left no trace in
   the answer - on the surface that loops over every expiry and title. Every
   section's coverage is now collected in _Context.search_coverage and merged
   into the scan's pair_search; capped is sticky and capped_sections counts the
   cut ones.

2. The ceiling bounded the output, not the work. The wide branch built the
   complete n^2/2 list before trimming it, so pair_max_width=100000 on a long
   chain allocated everything first. The limit is enforced inside the inner
   loop now. With that, truncation is a CUT in enumeration order and no longer
   "the narrowest pairs" - the docstring, README and doc say so, and a capped
   search reports possible_exact: false so nobody prints a reassuring "N von N".

3. pair_max_width=0 without a mode produced a 500. The derived path had no
   positive-width guard, validate() accepted it and form_vertical_pairs raised
   inside vertical_spreads ("pair search 'within_width' needs a positive
   max_width"). Measured, then fixed: 400 with "pair_max_width: eine positive
   Breite erwartet (ist: 0.0) ... 0 ist keine Suche". A negative width keeps its
   own single rule instead of a second message.

Measured: 977 passed, 202 subtests, ruff clean. Live: /api/screen?pair_max_width=0
-> 400; a capped search reports {"capped": true, "possible_exact": false,
"enumerated": 100, "limit": 100} and the page prints "gekappt bei 100; die Suche
ist damit NICHT vollstaendig".
